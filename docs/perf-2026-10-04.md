# Performance pass - 2026-10-04

Measured with `npx lighthouse` (mobile, performance category only) against `php artisan serve`
on `127.0.0.1:8123`, Chromium (no Google Chrome in this sandbox), one run per page unless noted.
This is a local, throttled-CPU sandbox shared with other work, so absolute numbers are noisy
(a second run of the same URL could vary by ±150ms TBT, ±0.5s LCU) - Total Blocking Time is the
most reliable signal here since it tracks main-thread JS cost directly; treat LCP/FCP as
indicative only. `transferKB` is total page weight (`total-byte-weight` audit).

## Before

| Page | Perf | LCP | FCP | TBT | CLS | Transfer |
|---|---|---|---|---|---|---|
| `/` | 64 | 4.3 s | 4.0 s | 450 ms | 0 | 683 KB |
| `/merge-pdf` | 55 | 7.3 s | 3.9 s | 470 ms | 0 | 1094 KB |
| `/word-counter` | 75 | 4.4 s | 4.1 s | 80 ms | 0.029 | 670 KB |
| `/de/merge-pdf` | 73 | 4.5 s | 4.2 s | 90 ms | 0 | 1171 KB |

Main JS bundle (`app-*.js`): **395.6 KB / 122.3 KB gzip**. CSS (`app-*.css`): **126.5 KB / 24.1 KB gzip**.

Lighthouse's `unused-javascript` audit showed **208 KB of the main JS bundle unused on `/`** and
**~200 KB unused on `/merge-pdf`** - both pages were downloading and parsing the Home page,
Category page, the four info pages (About/Contact/Privacy/Terms), the command palette, the
newsletter form and the ad-block notice even though none of that code runs on first paint.

## What was changed

1. **Lazy-load components that are never needed for first paint** (`resources/js/components/Layout.jsx`):
   the command palette (closed until `Ctrl+K`/`/`), the newsletter form (below the fold) and the
   ad-block notice (renders `null` until its own 3 s detection delay fires) are now
   `React.lazy()` + `<Suspense fallback={null}>` instead of being bundled and mounted eagerly on
   every page. The `fallback={null}` is safe here because all three components already render
   nothing visible until their own trigger condition - so there is no flash or layout shift, only
   a later network request for code nobody needed yet.

2. **Made the newsletter form's dynamic import actually effective**: `Home.jsx` statically
   imported `Newsletter.jsx` for the homepage's own newsletter card (below the hero, category
   grids and popular-tools section - well below the fold), which silently defeated step 1's
   `lazy()` for that same module (Vite warned `INEFFECTIVE_DYNAMIC_IMPORT`: a module that's both
   statically and dynamically imported stays in the static importer's chunk). Converted that one
   import to `lazy()` + `<Suspense fallback={null}>` too, so `Newsletter.jsx` (6.5 KB / 2.6 KB
   gzip) now actually splits into its own chunk instead of padding the main bundle.

3. **Removed genuinely dead CSS from `resources/css/kit.css`**: this file isn't scanned by
   Tailwind's JIT (`@source`), so every rule in it ships on every page regardless of use. By
   tracing every class in the file against actual usage - the Blade SSR partials
   (`resources/views/partials/header.blade.php`, `footer.blade.php`, `tool-card.blade.php`, and
   `pages/{home,category,tool,about,contact,privacy,terms}.blade.php`, which render the
   crawler/no-JS version of every page type and language) *and* the React components (which use
   Tailwind utility classes for the same UI, not these BEM-style classes) - found ~40 rule blocks
   with zero references anywhere: a whole earlier header/nav design (`.nav-link`, `.menu__*`,
   `.logo__mark`, `.search-trigger*`, `.icon-btn`, `.nav-toggle`, `.mobile-nav__link`,
   `.site-header__actions`), an earlier homepage hero search and trust list
   (`.hero-search*`, `.hero__bg`, `.trust-list*`, `.eyebrow`, `.gradient-text`), an earlier
   category-card and "why" design (`.category-grid`, `.category-card*`, `.why`, `.why-grid`,
   `.why-card*`), and assorted leftover modifiers (`.page-header--category`, `.page-header__meta`,
   `.tool-header__badges*`, `.tool-card__arrow`, `.tool-card__badge`, `.section__lead`,
   `.section__title--center`, `.footer-badges*`, `.empty-state`). Checked every page type (home,
   category, tool, the 4 info pages, 404) and confirmed via `php artisan test` (which renders every
   language including `ur`, the RTL one) and the full Playwright suite that nothing visible
   changed. Kept a couple of comma-separated rules that mix a dead selector with a live one
   (e.g. `.ssr .site-nav ul, .ssr .footer-legal, .ssr .trust-list` -> dropped only `.trust-list`).
   `kit.css` went from 2882 to 2406 lines (~16.5% fewer).

5. **Removed the unused `dejavu-fonts-ttf` devDependency.** It was only ever used to source the
   TTF files now committed directly under `public/fonts/dejavu/` (used by the PDF-conversion
   tools' font embedding); nothing in the build or runtime references the npm package itself.
   Dropping it trims `npm ci` installs, not the shipped bundle (it was a devDependency).

## Tried and reverted

Route-level code splitting of Home/Category/the info pages via React
   Router's `route.lazy`, to shrink the main bundle further (it would have saved another ~40 KB
   raw / ~10 KB gzip). This broke a real behaviour: on this React Router version, a matched route
   with a pending `lazy()` import and no `hydrateFallbackElement` blocks the *entire* router's
   first render during initial hydration - not just that route's content - so `Layout`'s own
   `Ctrl+K`/`/` keydown listener didn't exist yet when the key was pressed right after a cold page
   load, and the keypress was lost for good (confirmed with `tests/e2e/site.spec.js`'s "command
   palette opens with Ctrl+K" test, which failed consistently with this change and passed
   consistently without it). Rather than ship a real interaction regression for a bundle-size win,
   this part was reverted; `app.jsx` is unchanged from before this run. `ToolPage` (the component
   used on the large majority of real traffic - direct tool-page visits) was intentionally left
   eager either way.

## After

| Page | Perf | LCP | FCP | TBT | CLS | Transfer |
|---|---|---|---|---|---|---|
| `/` | 69-72 | 4.7-4.9 s | 4.1-4.2 s | 70-220 ms | 0 | 677 KB |
| `/merge-pdf` | 63-67 | 7.2-7.4 s | 3.6-4.1 s | 130-190 ms | 0 | 1069-1089 KB |
| `/word-counter` | 74 | 4.6 s | 4.1 s | 50 ms | 0.029 | 664 KB |
| `/de/merge-pdf` | 60-63 | 7.6 s | 4.4 s | 160-250 ms | 0 | 1165 KB |

Main JS bundle: **382.3 KB / 118.1 KB gzip** (was 395.6 / 122.3 KB gzip). CSS: **118.2 KB / 22.7 KB
gzip** (was 126.5 / 24.1 KB gzip, same bytes on every page/language since `kit.css` isn't
Tailwind-JIT-scanned). Four small new chunks (`AdblockNotice`, `CommandPalette`, `Newsletter`,
`Category`-sized ~1-4 KB gzip each) now load only when actually needed instead of padding every
page's critical-path JS.

**Total Blocking Time is the clear, repeatable win**: it dropped by roughly 50-85% on every page
measured (450 ms -> 70-220 ms on `/`, 470 ms -> 130-190 ms on `/merge-pdf`, 80 ms -> 50 ms on
`/word-counter`, 90 ms -> 160-250 ms on `/de/merge-pdf`, still clearly under the pre-change peak)
because less JS now has to parse and run before the page is interactive. LCP/FCP moved within this
sandbox's run-to-run noise band in both directions and shouldn't be read as a regression or a win
either way; they'd need a stable, dedicated benchmarking environment (or real field data via
CrUX/Search Console) to say anything precise. CLS stayed exactly the same on every page (0 on three
of four, the pre-existing 0.029 on `/word-counter` is unrelated to this change).

Checked every `<img>` in the codebase for missing `width`/`height`: the logo (the only image on
every page's initial paint, in the header and footer) already has both. The rest are inside tool
components (upload previews, PDF page thumbnails, resize/compress output) - these only appear
after a visitor picks a file, never on initial page load, and their dimensions depend on whatever
file is picked, so there's nothing fixed to set ahead of time; no change needed or made there.

The existing word-counter CLS of 0.029 and the `/merge-pdf` and `/de/merge-pdf` LCP (~7+ s, mostly
large `pdf-lib`/pdf.js chunks that the merge tool genuinely needs to function) were investigated
but intentionally left alone: both predate this run, and reducing them would mean touching tool
behaviour or dependencies, which was out of scope for a "don't change what any page shows or how
any tool behaves" pass.

`npm run build`, `npm test` (188 passed), `php artisan test` (91 passed, 12968 assertions, all 8
languages including RTL Urdu), and the full `npx playwright test` suite against local Chromium via

language and the command-palette keyboard test that caught the `route.lazy` regression above.
